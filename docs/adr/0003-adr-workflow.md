# ADR 0003: Nygard形式のADRを開発フローに組み込む

Date: 2026-10-03

## Status

Accepted

採用確認: [PR #21](https://github.com/rion0918/pop-reminder/pull/21)。ユーザーのmainへのマージ指示を受けて採用した。

## Context

ADRを作成しても、開発中の参照や新しい判断の記録に十分使えていなかった。書く負担を抑えながら、開発者とエージェントが採用理由や受け入れた欠点を確認できる運用が必要である。

## Decision

Nygard形式の短いADRを `docs/adr/` で管理し、作業開始時とPRで参照する。1件に1つの判断を記録し、Status・Context・Decision・Consequencesと日付を持たせる。項目が少なく、背景・結論・影響を短く残せるため採用する。

相談が必要な判断にはGitHub Discussionsを使い、決まった内容をADRにまとめて相互リンクする。ユーザーの採用確認後にAcceptedとし、判断が変わる場合は新しいADRで置き換える。具体的な手順と一覧は [運用ガイド](README.md) に置く。

見送った選択肢:

- MADRの詳細なテンプレート: 比較を整理しやすいが、初回は記録・参照の習慣を作るため項目数を抑える。
- Discussionsだけで決定を管理: 議論を追いやすいが、コードと一緒に判断を参照・レビューできるリポジトリの記録を持ちたい。
- ADR Syncによる双方向同期: 本文を二重管理する運用と同期の保守を増やすため、初回はリンクで接続する。

## Consequences

- 利点: 判断の理由とトレードオフをコードと一緒に読み、PRで確認できる。
- 利点: 必要な議論はDiscussionに残し、コメントの経緯から決定へたどれる。
- 受け入れる欠点: 選択肢の比較は自由記述になるため、採用理由や欠点が薄くないかレビューが必要になる。
- 受け入れる欠点: ADR一覧の状態と、利用したDiscussion・PRへのリンクは手動で更新する。

確認方法: 「既存判断に従う変更」「新しい技術選定」「判断の置き換え」で、読む記録と残す内容を運用ガイドから判断できることを確認する。

見直す条件: 記録・参照が続かない、または選択肢の比較や手動のリンク更新が負担になったときに、形式や連携方法を再検討する。
