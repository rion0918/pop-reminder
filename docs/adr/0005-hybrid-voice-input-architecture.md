# ADR 0005: 傾けて音声入力の認識精度向上のためOSハイブリッド認識とOrca式音声処理パイプラインを採用する

Date: 2026-11-13

## Status

Proposed

## Context

「ふわっと。」の傾けて音声入力（Raise to Speak）は、これまで完全オフライン動作（`requiresOnDeviceRecognition: true` および Android 13 以上の導入済みオフライン言語パック必須、未導入時はアプリ同梱の `moonshine-tiny-ja` へのフォールバック）を前提としていた。

しかし実運用において以下の課題が顕在化した。

1. Android 端末の大半では日本語オフラインモデルが初期導入されておらず、超軽量な `moonshine-tiny-ja`（約30MB）へ常時フォールバックし、日常の日本語発話や日時表現の認識精度が著しく低かった。
2. iOS・Android ともに `requiresOnDeviceRecognition: true` を強制していたため、OS 標準の高精度なサーバー併用音声認識（Apple Siri / Google Speech）を利用できなかった。
3. 傾き検知後に BottomSheet の展開完了を待ってからマイクを起動していたため、傾けた直後の話し始め（語頭）が欠落しやすかった。
4. 音声認識完了時の日時・タイトル自動解析（`parseVoiceReminder`）が Android のみに限定され、iOS で機能していなかった。

一方、デスクトップ環境で高い日本語認識品質を実現している Orca の音声入力実装を調査したところ、コンテキスト語彙の注入、話し始めを取りこぼさないバッファリング、日本語フィラー除去（`えーと`・`あのー` 等の長音・促音と直後の句読点処理）、無音エネルギー最小点でのチャンク分割といった前後のパイプライン設計が品質を支えていることが確認できた。

## Decision

完全オフライン限定の制約を解除し、B2C モバイルアプリとして追加の API キー設定や大容量モデル同梱を必要としない「OS ハイブリッド音声認識 + Orca 式音声処理パイプライン + ローカルフォールバック」の構成を採用する。

1. **OS ハイブリッド音声認識の解禁とドメイン語彙注入**:
   - `voiceInputServiceCore` の既定値を `requiresOnDeviceRecognition: false` とし、オンライン時は OS の高精度認識、オフライン時は OS オンデバイス認識を自動利用する。
   - Android の OS 音声認識プロバイダも Android 9（API 28）以上でオンライン・オフライン兼用の標準 `SpeechRecognizer`（`interimResults: true`）を第一候補とし、Android 13 以上ではバックグラウンドでのオフラインモデル準備も継続する。
   - Orca の語彙ヒントと同様に、`contextualStrings` へリマインダー特有の語彙（日付・時刻・終日・操作語）を注入し、iOS の `iosTaskHint` を `'dictation'` に設定する。
2. **Orca 式音声・テキスト処理パイプラインの移植**:
   - 日本語フィラー（`えーと`・`えっと`・`あのー`・`うーん`・`んー` 等）および直後のポーズ記号を除去する正規化処理を音声認識結果と日時パーサー前段に組み込む。
   - PCM 録音ストリームを用いるプロバイダ向けに、Orca と同等の最小エネルギー地点チャンク分割と 16kHz 16-bit Mono WAV エンコード処理を備える。
3. **傾けて音声入力（Raise to Speak）の即時起動と iOS / Android 共通パース**:
   - Quick Add シートが音声モードで開かれた際、シート展開アニメーション完了を待たずに録音を開始し、語頭欠落を防ぐ。
   - 音声入力完了時の `parseVoiceReminder` によるタイトル・日付・時刻・終日の自動反映を iOS・Android 共通で適用する。

検討した他案と見送り理由:

- **案A: Whisper Large v3 Turbo（約886MB）の端末内バンドルまたは必須ダウンロード**
  - モバイルアプリの配布サイズおよび初回待機時間として過大であり、「数秒でリマインダーを残す」体験を損なうためデフォルト採用は見送った。
- **案B: 全ユーザーの音声を独自クラウド API（OpenAI / Groq Whisper API）へ常時送信する構成**
  - サーバー維持費・API 従量課金・鍵管理が必要となるため、標準のメイン経路としては OS ハイブリッド音声認識を優先し、WAV エンコーダ等は拡張可能なモジュールとして保持する形とした。

## Consequences

- 利点:
  - API キー設定やアプリサイズの増加なしに、iOS・Android の両方で商用水準の日本語認識精度とリアルタイム表示が得られる。
  - 傾けた直後の発話の取りこぼしが減り、iOS でも発話から日時・タイトルが自動設定される。
  - OS 音声認識が利用できない環境やオフライン環境でも、OS オンデバイス認識および既存の同梱 `Moonshine` フォールバックにより動作を維持できる。
- 受け入れる欠点:
  - `requiresOnDeviceRecognition: false` により、オンライン時は OS 提供者（Apple / Google）の音声認識サーバーが利用される場合がある。
- 確認方法: `pnpm run mvh:verify` による単体テスト・ソース契約テスト・型チェック・Lint の通過を確認する。
